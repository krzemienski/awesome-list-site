### Defect found and fixed: merge kept running across an account switch

**Before the fix** (in-SPA switch, first run of this script): the run started for A never stopped. After the switch, the A run and two more runs all ran at once, so each id was POSTed **3 times** (9 POSTs for 3 ids: `POST /api/bookmarks/184743` at +4.5 s, +5.7 s, +7.0 s, and the same for 184744 and 184745). The run A started sent its POSTs with B's session cookie. Every POST is an upsert that resets the note and saved date, so overlapping runs can overwrite a save another run just wrote.

**Root cause:** `GuestBookmarkMerge` reset its one-shot guard whenever the account went signed-out, but the run already in progress kept looping. Nothing tied a run to the account that started it, and nothing stopped two runs from overlapping.

**Fix:** `client/src/components/auth/GuestBookmarkMerge.tsx`:
- each run stores the server user id and the Clerk user id it started with, and checks both, read live, before every detail request and every POST. If the account changed, the run stops (`interrupted`), leaves unsent ids on the device and shows no toast;
- runs go through a single queue, so a new account's run starts only after the earlier one has stopped;
- the attempted flag is now stored per account, so switching directly from one account to another also gets a run.

**After the fix** (same script, in-SPA and full-load modes): A's run made one detail request, then stopped without any POST. B's single run POSTed each id **exactly once** (`184743` +8.5 s, `184744` +12.6 s, `184745` +16.8 s). Toast: "3 saved resources from this device are now in your account." A has none of the three; B has all three. The device's guest saves go to the account that is signed in when they are sent. An account never receives another account's data.
