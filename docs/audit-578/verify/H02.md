# H02 — Search HTML ignores filters, sorting, filter-only browsing and the legacy `search` query

**Status: FIXED and proven on DEV (2026-10-09).**

## Before (from the audit)
- `/search?q=video&category=encoding-codecs&sort=name-asc`: server HTML started with ids 185179, 185282…, but the client API returned total 224 starting with 185062, 186483….
- The filter-only URL `/search?category=encoding-codecs` and the alias URL `/search?search=ffmpeg` rendered no server result links at all.

## Fix
- og-middleware's search section now parses the URL with the same shared discovery-params parser the client uses (q/search alias, category/subcategory, tags, format, provider, skill, sort, page).
- It runs the same public-discovery query the client's API call runs, including filter-only browsing, and renders that page slice.
- The client and server share the `searchPageSeo` title template, so titles agree. Pages stay `noindex, nofollow` with no canonical.

## Recipe executed
Script: `evidence-587/parity.mjs` (search cases: `evidence-587/search-cases.json`). For each URL it:
1. curls the server HTML and extracts result ids, the total, the title, robots and canonical;
2. calls the exact client API (`/api/search/...` with the same params);
3. loads the page in real Chromium and reads the settled DOM ids, chips, order and title.

Raw results: `evidence-587/search-editorial-1440.json`, `evidence-587/search-brutalist-390.json`.

| Combo | URL | HTTP | SSR total | API total | SSR ids = API ids = DOM ids | Titles equal | robots | canonical |
