# D09: A failed resource delete destroyed edit suggestions and wrote a false deletion audit row (VERIFIED)

**Environment.**
- Scratch DB `awesome_scratch_590`, a `pg_dump` clone of DEV (1993 resources).
- **After fix:** the working tree on port 5190 (`DATABASE_URL=<scratch> PORT=5190 DISABLE_BACKGROUND_JOBS=1 npx tsx server/index.ts`).
- **Before fix:** an untouched copy of the pre-fix code on port 5191, against the same scratch DB. This is HEAD 3e85c8b7: the six changed server files were restored with `git show HEAD:<file>` into `/tmp/old590`.
- Background jobs were disabled on both instances, so no scheduler and no paid AI ran. These are failure-injection proofs, not global operations.
- The plain recipe was also run once against the DEV app (workflow "Start application", port 5000) after the fix.
- Admin calls use the `X-Admin-Audit-Key` header (the value comes from the ADMIN_PASSWORD secret and is never logged) plus `Origin: <base url>`.

**Harness.**
- `evidence-590/harness/lib.mjs` wraps real fetch and psql, and records every request, status, response and SQL result.
- `evidence-590/harness/d09-delete.mjs` is the proof script.
- Fixtures all start with `__qa_test_plan_590_d09_`:
  - a QA user
  - an approved resource
  - a **pending** `resource_edits` row
  - a draft journey with three logical steps, where step 1 links to the resource
  - `user_journey_progress` with `current_step_id = step 1` and `completed_steps = [step1, step2]`
  - one favorite and one bookmark of the resource
- Teardown deletes by exact id, then runs this residue query:

## Before (pre-fix code, executed 2026-10-10 14:11 UTC)
`PROOF_DATABASE_URL=<scratch> BASE_URL=http://127.0.0.1:5191 node d09-delete.mjs logs/D09-before-oldcode.json`. Log: `evidence-590/logs/D09-before-oldcode.json`.

The request was `DELETE /api/admin/resources/188653`, which returned **500** `{"message":"Internal Server Error"}`.

| | resource_rows | edit_rows (pending) | deleted audit rows | progress.current_step_id |
|---|---|---|---|---|
| before DELETE | 1 | 1 (1) | 0 | 279 |
| after DELETE | **1** | **0 (0)** | **1** | 279 |

This is the audit's finding exactly: the resource survived, its pending edit suggestion was destroyed, and the audit log says it was deleted.
- **Cause:** the audit insert and the `resource_edits` delete were separate statements outside a transaction.
- The cascading `journey_steps` delete was then refused by `user_journey_progress.current_step_id`, a FK with no ON DELETE action.

## Fix
`ResourceRepository.deleteResource` now runs as **one** `db.transaction`. In order:
1. Lock the resource row `FOR UPDATE`. A missing row throws `ResourceNotFoundError`, which returns 404.
2. Count the edits and pending edits, then delete the `resource_edits` rows.
3. Null out `research_discoveries.created_resource_id`.
4. Call `LearningJourneyRepository.clearProgressPointersToResource(tx, id)`, the journeys progress-pointer helper. It removes the linked step rows, renumbers the remaining logical steps, re-points or nulls `current_step_id`, and drops removed step ids from `completed_steps`.
5. Write the single `deleted` audit row, with the acting admin and `changes.cleanup` counts.
6. Delete the resource. Favorites and bookmarks cascade.

Public caches are invalidated only after commit. If any statement fails, the whole transaction rolls back. A FK refusal (`23503`) becomes a `ConflictError` naming the blocking table. The single DELETE route answers that with **409**. The bulk delete puts the same message in its `failures[].reason` and returns 409 when nothing was deleted. A successful single DELETE returns `{message, cleanup}`.

## After: refused delete changes nothing (real FK refusal injected)
`--blocker` creates a QA table on the scratch DB, `__qa_test_plan_590_blocker(resource_id integer references resources(id))`, with no ON DELETE action, and adds one row pointing at the fixture resource. That makes the transaction's **final** statement fail after the edits, steps, progress pointer and audit row were already written inside it. The blocker table is then dropped and the delete retried.

**Single DELETE:** `node d09-delete.mjs logs/D09-after-single.json --blocker`, run 14:12 UTC. **14 PASS, 0 FAIL.**
- The refused `DELETE /api/admin/resources/188654` returned **409**: `"Resource #188654 could not be deleted because records in __qa_test_plan_590_blocker still reference it. Nothing was changed; remove or reassign those records and try again."`
- The snapshot after the refusal is **identical** to the snapshot before it. Both read: resource 1, edit 1 (still pending), deleted-audit 0, steps `[282→res, 283, 284]`, progress `current_step_id 282`, `completed_steps [282,283]`, favorites 1, bookmarks 1.
- After the blocker was dropped, the retry returned **200** with `{"message":"Resource deleted successfully","cleanup":{"removedEdits":1,"removedPendingEdits":1,"removedJourneySteps":1,"detachedDiscoveries":0}}`.
- After the retry:
  - The resource is gone, its edits are gone, and favorites and bookmarks are 0.
  - Exactly **one** `deleted` audit row exists, with `performed_by` = the admin id, `original_resource_id = 188654`, and cleanup counts recorded.
  - The remaining steps were renumbered `[{283,n:1},{284,n:2}]`.
  - Progress survives: `current_step_id = null`, `completed_steps = [283]`, `completed_at = null`. There is no dangling pointer, and the user keeps credit for step 2.

**Bulk delete:** `node d09-delete.mjs logs/D09-after-bulk.json --blocker --bulk`, using `POST /api/admin/resources/bulk/delete`. **14 PASS, 0 FAIL.**
- The refusal returned **409**: `"No resources were deleted; 1 failed (#188655: Resource #188655 could not be deleted because records in __qa_test_plan_590_blocker still reference it. Nothing was changed; …)"`, with `failures[0].reason` set to the same message. The state was unchanged.
- The retry returned 200 (`"Deleted 1 resource(s)"`), with the same cleanup and audit results as the single path.

## After: the audit's original recipe (no injected blocker)
- **Scratch:** `node d09-delete.mjs logs/D09-after-plain.json`. The progress row's `current_step_id` points at the linked step, which is exactly the case that returned 500 before. The DELETE now returns **200** with cleanup counts, and the invariant holds.
- **DEV app (port 5000):** `PROOF_DATABASE_URL=$DATABASE_URL BASE_URL=http://127.0.0.1:5000 node d09-delete.mjs logs/D09-dev-plain.json`. This also returned **200** with `cleanup {removedEdits:1, removedPendingEdits:1, removedJourneySteps:1, detachedDiscoveries:0}`, and the invariant holds.
- Note: in this mode the script prints the label "BEFORE-run outcome" whichever code it runs against. The status and body show which run it was.

The SQL never showed a surviving resource together with a deleted edit or a false `deleted` audit row in any post-fix run.

**Residue:** every run ended with `{"resources":0,"edits":0,"journeys":0,"steps":0,"progress":0,"users":0,"blocker_table":0}`.
