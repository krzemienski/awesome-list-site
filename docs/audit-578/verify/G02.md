# G02: Research approval could publish a resource without recording the approved discovery (VERIFIED)

**Environment.** Scratch DB `awesome_scratch_590`, a `pg_dump` clone of DEV. The same two instances as D09 were used, both with background jobs disabled:
- **After fix:** the working tree on port 5190.
- **Before fix:** the pre-fix code (HEAD 3e85c8b7) on port 5191.

Admin calls use the `X-Admin-Audit-Key` header plus `Origin`.

**Harness.** `evidence-590/harness/g02-g03-approve.mjs`, run with `PROOF_DATABASE_URL=<scratch> BASE_URL=<instance> node g02-g03-approve.mjs <out> [--before]`.

**Fixtures** all start with `__qa_test_plan_590_g02_`:
- A completed research job with one `pending_review` discovery. Its suggested taxonomy is the existing *Intro & Learning › Learning Resources* plus a **new** sub-subcategory `__qa_test_plan_590_g02_<stamp> node`, so approval must auto-create a taxonomy node. That makes taxonomy residue observable.
- A second job with two discoveries, used for bulk approval (see G03).

**Failure injection.** A real constraint was added on the scratch DB, so the **discovery-update** step fails after the taxonomy insert, the resource insert and the publication transition have already run:

```sql
alter table research_discoveries add constraint __qa_test_plan_590_block
  check (not (status = 'approved' and title like '__qa_test_plan_590_g02_%')) not valid;
```

## Before (pre-fix code, executed 2026-10-10 14:12 UTC)
Log: `evidence-590/logs/G02-G03-before-oldcode.json`.

The request `POST /api/researcher/discoveries/84/approve` with the constraint in place returned **500**. State after the call:

`resources 0, discovery pending_review, job counter 0, taxonomy_nodes 1, audit_rows 0`

The pre-fix code had already wrapped the resource insert in a transaction, so no public resource leaked. But the **sub-subcategory was created outside the transaction and survived the failed approval** as taxonomy residue.

After the constraint was dropped, the retry returned 200. The resulting resource had `approved_at NULL`, `approved_by NULL`, `status_changed_at NULL` and **no audit row** (this is G03's defect).

## Fix
`researchService.approveDiscovery(id, {actorId})` now runs entirely inside `withResourcePublication`, the shared publication helper's transaction:
1. Lock the discovery row `FOR UPDATE`. An already-approved discovery that has a `createdResourceId` is returned unchanged (idempotent). Any other non-pending state returns 409.
2. Run the normalized duplicate-URL guard on the transaction. A duplicate returns 409 with an actionable message.
3. Run `ensureSubSubcategoryExists` through a **transaction-backed** taxonomy accessor, so the node commits or rolls back with the approval.
4. Insert the resource as `pending`, then call `transitionResourceInTransaction(… {status:'approved'}, actorId, {expectedStatus:'pending', notes:'AI researcher approval: discovery #N (research job #M)'})`. This step applies the description gate, approval provenance and the audit row (see G03).
5. Update the discovery with a `status = 'pending_review'` guard and link `created_resource_id`.
6. Increment `research_jobs.approved_discoveries`.

Public caches (resource publication, plus `category-mutation` when a node was created) are invalidated **only after commit**.

## After (executed 2026-10-10 14:12 UTC, port 5190)
Log: `evidence-590/logs/G02-G03-after.json`. **15 PASS, 0 FAIL.** The G02 checks:

| Step | HTTP | resources | discovery | created_resource_id | job counter | taxonomy node | audit rows |
|---|---|---|---|---|---|---|---|
| start | – | 0 | pending_review | null | 0 | 0 | 0 |
| approve, constraint present | **500** | **0** | **pending_review** | null | **0** | **0** | **0** |
| constraint dropped, retry | 200 | 1 (approved) | approved | 188660 | **1** | 1 | 1 |
| retry again | 200 | 1 | approved | 188660 | **1** (no 2nd increment) | 1 | 1 |

- The failed approval left nothing behind: no resource, no taxonomy node, no audit row, an unchanged counter and a still-pending discovery. That is why the retry could finish the original approval.
- Exactly one approved resource, one approved discovery and one counter increment resulted. The repeated approve is idempotent.
- The 500 body is the generic contract-masked "Internal Server Error". This is acceptable for an induced database fault. Business conflicts (an already-reviewed discovery, a duplicate URL) return 409 with an explanatory message.

**Residue:** `{"resources":0,"discoveries":0,"jobs":0,"taxonomy_nodes":0,"constraints":0}`. The injected constraint was dropped in teardown, with an `if exists` fallback.

**Teardown.** The scratch instances were stopped and `awesome_scratch_590` was dropped on 2026-10-10 (verified: `select count(*) from pg_database where datname like 'awesome_scratch_590%'` → 0). DEV residue for `__qa_test_plan_590%` (resources, users, journeys, discoveries) → `0|0|0|0`.
