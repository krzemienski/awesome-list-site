# E01: A deleted Clerk account could be re-created by its still-valid session

**Status: FIXED, proven on DEV (2026-10-09)**

## Root cause (confirmed)
`DELETE /api/admin/users/:id` removed only the local `users` row. Clerk session JWTs are verified offline, so the
deleted user's browser kept a valid token. On its next request `clerkAuth.ensureDbUser` JIT-inserted the missing
bridge identity as `role=user`, which brought the account back.

## Fix
Permanent-deletion policy: the account is gone from both identity stores, and existing tokens cannot re-provision it.
- `server/lib/clerkAccountDeletion.ts`: resolves the Clerk user for a bridge id. A Clerk-native id (`user_…`) is
  looked up directly; a legacy id goes through the Clerk `external_id` lookup. That Clerk user is deleted **first**,
  which also revokes all of its sessions. If Clerk fails with anything other than a 404, the request fails closed
  (502) and the local row is kept.
- `migrations/0053_deleted_user_tombstones.sql` (idempotent) and the `deletedUserTombstones` entry in
  `shared/schema.ts` add a durable tombstone keyed by bridge id, plus the Clerk user id. It is written in the same
  transaction as the local delete (`UserRepository.deleteUserWithCleanup`).
- `server/clerkAuth.ts`: JIT provisioning checks the tombstone by bridge id OR Clerk user id. When one matches it
  refuses to insert and logs `refusing JIT provisioning for deleted account …`. The request is then treated as
  unauthenticated.
- `UsersTab.tsx`: the delete dialog now says the sign-in identity is removed and the account cannot be re-created by
  an existing session. Catalog submissions are detached (`submitted_by = NULL`), not deleted.

## End-user recipe (executed)
Script: `/tmp/e01/run.mjs`, Playwright with two browser contexts, against `npm run dev` on :5000. Full log:
`logs/E01-run.txt`.

1. Created a DEV Clerk QA user `__qa_test_plan_e01_1791562236876+clerk_test@example.com` (external_id = bridge id).
   Signed it in through the real Clerk UI in **context B**.
   `/api/auth/user` returned `{"isAuthenticated":true,"id":"__qa_test_plan_e01_1791562236876","role":"user"}`.
2. Created a pending fixture resource 188645 with `submitted_by` set to that user.
3. **Context A** (owner admin) opened `/admin#users`, clicked Delete on the row and confirmed in the dialog.
   - `DELETE → 200 {"success":true,…,"clerkIdentity":"deleted","resourcesDetached":1,"editsDeleted":0}`
   - Clerk `GET /v1/users/<id>` afterwards: **404**
   - Tombstone row: `__qa_test_plan_e01_1791562236876|user_3KSsKTUUyHUvjxh4zS4ku1DoMAD|<admin id>|2026-10-09 16:11:03`
4. Polled every 10 s for **94 s** with context B's old `__session` cookie and the same token as a Bearer. The JWT
   expiry was 16:11:48, so polling continued well past it:
   ```
   poll 1  t+3s  cookie=200 {"a":false,"u":null} bearer=200 {"a":false,"u":null} bookmarks=401 sqlRows=0
   …
   poll 10 t+94s cookie=200 {"a":false,"u":null} bearer=200 {"a":false,"u":null} bookmarks=401 sqlRows=0
   ```
   The local row never came back. Before this run, in the first attempt, the server logged
   `[clerkAuth] refusing JIT provisioning for deleted account __qa_test_plan_e01_1791562044242` for the in-flight token.
5. Context B navigating to `/profile` was redirected to `/sign-in?redirect_url=%2Fprofile`.
6. Re-sign-in with the same email showed Clerk's **"Couldn't find your account."** The SQL row count stayed 0.
7. Catalog content after the delete: `188645|__qa_test_plan_e01 resource|pending|submitted_by=NULL` (detached, kept).

tombstones for `__qa_test_plan_e01_1791562044242` and `__qa_test_plan_e01_1791562236876`, and the user.deleted audit
rows 18063/18064, were deleted by exact id. Residue check (2026-10-09 16:36 UTC):
