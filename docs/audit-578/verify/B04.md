# B04 — Rapid clicks across steps overwrote queued completions

**Status: FIXED and proven** in a real browser on DEV `/journey/7`, signed in, at desktop 1366px and mobile 390px (touch), 2026-10-09.

## Before (audit evidence)
Code trace: `JourneyDetail.tsx` kept a single global `pendingDesiredRef`. While step A's PUT was in flight, clicking B then C replaced B with C, so B's completion was lost.

## Fix
`client/src/pages/JourneyDetail.tsx`:
- Pending intent is now kept **per logical step** (a map keyed by step number).
- The drain loop sends every distinct pending step in turn. Repeated clicks on the same step coalesce, and the last click wins.
- When a PUT fails, the client restores the snapshot and re-applies the queued clicks on other steps, so one failure does not discard other steps' intent.

## Proof — `task581-harness/browser-b04.mjs` → `out/browser-b04.json`
Throwaway Clerk user signed in via ticket. Every `PUT /api/journeys/7/progress` was held 2.5 s by Playwright `page.route` and then **continued to the real server** (or forced to fail once in scenario 3).

## Review follow-up (2026-10-10): queued write fails, refetch unavailable

**Reviewer finding:** when step B is clicked while A's PUT is in flight, B's optimistic flip is already in the cache when B's own mutation starts. Its `onMutate` snapshot therefore contained B, so a failed B rolled back to "B complete". In addition, a failed reconciling refetch replaced the whole loaded journey with the "Couldn't load this journey" panel.

**Fix (`client/src/pages/JourneyDetail.tsx`):**
- Track the last server-confirmed `completedSteps` for each write chain. It is seeded from the cache when a chain starts and updated from each successful PUT's `completedSteps`.
- A failed write rolls back to that confirmed state, then re-applies only the intents still queued.
- The full-page unavailable state now appears only when there is no loaded journey. A failed background refetch keeps the last loaded page.

**Proof:** scenario 4 of `task581-harness/browser-b04.mjs`. After scenarios 1–3, it clicks complete on step A=1 and then on B=5 while A is in flight. B's PUT (193-195) is forced to 500. Every `GET /api/journeys/7` is aborted (`internetdisconnected`) so the refetch cannot correct anything. The UI is read **without a reload**.
