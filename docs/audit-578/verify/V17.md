## 3. Repeat Pull: no duplicates, and the defect found here

| Step | Before | After |
|---|---|---|
| Pull 2, identical README (`V17-pull2-desktop.png`) | resources 8, v17 rows 3 | resources 8, v17 rows 3: **no duplicate rows** |

The job row, however, read **"Imported: 0; updated: 3; skipped: 0"**. `updated_at` changed on ids 9, 10 and 11, and the instance log shows:

```
↻ Updated: __qa_test_plan_592_v17 R1 - Updated content
↻ Updated: __qa_test_plan_592_v17 R2 - Updated content
↻ Updated: __qa_test_plan_592_v17 R3 - Updated content
```

**Root cause.** `checkConflict()` in `server/github/syncService.ts` compared fields with `!==`:
- The parser leaves absent hierarchy levels `undefined`.
- Stored rows hold `null`.
- So `undefined !== null` was true for every item without a sub-subcategory, and every unchanged re-import counted as an update. Each one also wrote `updated_at` and a "Updated from GitHub" audit row.

**Fix.** Fields are now compared nullishly (`(a ?? null) !== (b ?? null)`) over title, description and all hierarchy levels.

## 7. Invalid credentials (every source broken)

Instance C was re-spawned with `REPLIT_CONNECTORS_HOSTNAME=qa592-connector.invalid` and all three PAT variables set to an invalid token.

- Configure returned 400 "Configuration failed: Bad credentials".
- **UI Sync now**: job 9 `failed`, "Export failed: No working GitHub credentials. Re-authorize the Replit GitHub connection or refresh the GITHUB_PERSONAL_ACCESS_TOKEN secret." The remote head was **unchanged** (`V17-badcreds-sync-desktop.png`, opened). The log follows the credential chain:
  ```
  Replit GitHub connector unavailable: getaddrinfo ENOTFOUND qa592-connector.invalid
  GitHub personal access token was rejected by GitHub (bad credentials).
  ```
- **UI Pull**: job 10 `failed`, "Import failed: File not found: README.md in krzemienski/__qa_test_plan_592_gh". The private repo cannot be read, and the anonymous retry also returns 404 (`V17-badcreds-pull-desktop.png`).

**Fixture side effect, not a product defect.** The exported README writes the V16 headings verbatim as `__qa_test_plan_592_v16 Cat A`. On re-import, `normalizeCategory()` turns that into `qatestplan592v16 Cat A`, whose slug collides with the existing category, so the round trip reported 5 "Category hierarchy error … slug already exists" item errors.

This happens only because the QA names contain underscores, which the parser strips by design. No real category contains characters outside `[A-Za-z0-9 &-]`. The counts and errors were reported honestly (PARTIAL · 5 FAILED).

**Correction (found while preparing V18, fixed in section 9).** The slug collision itself is a fixture side effect, but what the import did next was a real defect. Every resource under the failed heading was still updated, and its `category` text was rewritten to `qatestplan592v16 Cat A`, a name with no matching taxonomy row. After that run, scratch rows 2/3/6/7/8 had orphan category text (`SELECT … category` returned `qatestplan592v16 Cat A` while `categories` held only `__qa_test_plan_592_v16 Cat A`). Orphan resources desync sidebar counts and browse pages.

## 9. Fix and re-proof: items under an unresolvable category are refused, not written as orphans

**Fix** (`server/github/syncService.ts`, import STEP 3/4): hierarchies that fail are recorded in a `failedHierarchies` map instead of a single hierarchy-level error. In STEP 4, each item under a failed hierarchy gets one item error (`Error processing <title>: Category hierarchy error: …`) and is skipped with `continue`. It is never created or updated. The outcome logic is unchanged: no successes means `failed` (422), some successes means `partial`.

**Scratch repair before the re-proof:** the five orphaned v16 rows had their category/subcategory/leaf text set back to the existing `__qa_test_plan_592_v16 …` names (UPDATE 5).
