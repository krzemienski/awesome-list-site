# E03: Signing back in lost the hash-routed admin tab

**Status: FIXED, proven on DEV (2026-10-09)**

## Root cause (confirmed)
`AdminGuard` and the AdminDashboard session-expired link built `redirect_url` from `pathname + search` only. The hash
(`#users`, `#journeys`, …) was dropped, so after signing in the admin landed on Overview.

## Fix
- `client/src/lib/returnUrl.ts`: one helper. `currentReturnPath()` returns pathname+search+hash.
  `normalizeReturnPath()` (used by `isSafeReturnPath()` / `requestedReturnPath()`) rejects any C0 control character or
  DEL, requires `/^\/(?![/\\])/`, then parses the value with `new URL(value, location.origin)`, requires the parsed
  origin to equal the current origin, and returns the **normalized** path+query+hash, which is what callers navigate
  to. This rejects `//host`, `/\host`, absolute URLs, and the control-character forms `/%0A/host`, `/%0D/host` and
  `/%09/host`. Before this, the browser's URL parser stripped the TAB/LF/CR and turned them into `//host`.
- `sanitizeRedirectParam()` runs on `/sign-in` before the fold step and before Clerk mounts. It drops an unsafe
  `redirect_url` (or rewrites it to its normalized form), so Clerk never reads a raw unsafe value.
- Both sign-in prompts use it: `AdminGuard`'s "Sign in to continue" and the dashboard's session-expired link
  (`signInHrefForCurrentLocation`). The owner-password sign-in and the Clerk redirect validate the target with the
  same rule.
- Fresh loads: the server's 302 to `/sign-in` cannot see the hash; `foldInheritedHashIntoRedirect()` (App boot) folds `location.hash` back into
  `redirect_url` before Clerk mounts.
