# B05 — Deleting a logical step could fail halfway

**Status: FIXED and proven** via API and a real browser at `/admin/journeys`, desktop 1366px and 390px, 2026-10-09.

## Before (audit evidence)
The UI deleted the 3 rows of a group with 3 separate requests. Row 271 → 200, then row 272 → **500** because QA progress referenced it. SQL then showed the group with only 2 rows. Renumbering ran outside the delete.

## Fix
- `LearningJourneyRepository.deleteJourneyStep(id, wholeGroup)` does all of the following in **one transaction**:
  - Deletes the row, or the whole `step_number` group when `?group=true`.
  - Reconciles every `user_journey_progress` row for the journey: removes deleted ids from `completed_steps`, nulls `current_step_id` when it pointed at a deleted row, and recomputes `completed_at`.
  - Renumbers the remaining groups contiguously.
  - Any failure rolls back everything.
- `JourneyStepsManager` sends a single `DELETE …/steps/:primaryId?group=true` for the Delete action.
- The response contract masks every 500 body as "Internal Server Error". The editor therefore shows an actionable message instead: "Nothing was changed because the server hit an error. Reload the steps and try again."
- Transaction-safe helper for the later deletion task: `learningJourneyRepo.clearProgressPointersToResource(tx, resourceId)`. It runs inside the caller's transaction and removes the resource's step rows with the same progress reconciliation and renumbering.
  - Proof (`out/clear-pointers.txt`): deleting a referenced resource without the helper is rejected with `23503 user_journey_progress_current_step_id_journey_steps_id_fk`. With the helper, 1 row is removed, steps renumber to 1,2, `current_step_id` becomes null, and `completed_steps` becomes `[293]`.

## Proof — API (`api-proof.json` → `B05`)
- Group rows 284/285/286 (step 1), 287 (step 2), 288 (step 3). Progress: `completed=[284,285,286,287]`, `current=285` (middle row).
- `DELETE …/steps/285?group=true` → 200. Steps become `287→1, 288→2`, with `completed=[287]` and `current=null`.
- Deleting referenced single row 289 → 200. Steps 1,2, `current=null`, and `completed_at` set because every remaining step is complete.

## Proof — browser (`browser-admin.mjs delete <vp>` → `out/browser-admin-delete-{desktop,390}.json`)
Throwaway Clerk user promoted to `role='admin'`. Draft QA journey:
- Group 1 = 3 rows (a1,a2,a3), group 2 = 2 rows (b1,b2), group 3 = 1 row.
- Progress `completed=[a1,a2,a3,b1,b2]`, `current=a2`.

1. **Failure path (whole group stays).** A temporary DEV-only `BEFORE DELETE` trigger raised an exception on **a3**, so a1 and a2 had already been deleted inside the transaction when it failed.
   - In the UI: Steps → Delete on step 1 → confirm. The server returned 500.
   - Toast: "Could not delete step — Nothing was changed because the server hit an error. Reload the steps and try again."
   - SQL: all 6 rows intact (a1, a2, a3 still `step_number=1`), progress unchanged. The UI still shows 3 groups.
   - The trigger and function were then dropped (residue check: 0).
2. **Success path.** Delete step 1 → confirm → 200. The group disappears.
   - SQL: `b1→1, b2→1, c→2`, progress `completed=[b1,b2]`, `current=null`.
   - The UI shows "1 · group2" and "2 · group3".
3. **Remove resource on a referenced row.** Progress `current` set to b2. Clicked "Remove resource #… from this step" on b2 → confirm → 200.
   - SQL: `b1→1, c→2`, `completed=[b1]`, `current=null`. Toast: "Resource removed from step".

Same results at desktop and 390px. At no point did SQL keep only part of a group.
