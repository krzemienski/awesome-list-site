**Status: PASS** (a defect was found and fixed: under a DB outage, a browser navigation got a raw JSON body instead of the app)

**Screenshots (opened and looked at):** `shots-592/V20-BEFORE-1440-categories-document-json.png`, `V20-1440-categories-error-card.png`, `V20-390-categories-error-card.png`, `V20-1440-home-error-card.png`, `V20-*-recovered.png`.

## How the outage is real (no mocks, no fabricated responses)
A separate pg connection to the **scratch DB only** runs `BEGIN; LOCK TABLE resources IN ACCESS EXCLUSIVE MODE` and holds it. Server queries then fail with SQLSTATE 55P03 (`canceling statement due to lock timeout`, about 2 s). `isDatabaseUnavailableError` turns that into the route's real `503 Retry-After: 1`.

Before each scenario the harness polls `/api/awesome-list/nav` until the 60-second public cache has expired and the route itself answers **503** (`{"message":"Service is temporarily unavailable"}`, about 2.05 s). The lock is released with `COMMIT` of an empty transaction, so nothing is written. The final check found `accessExclusiveLocksLeft: 0`.

## Defect found (before)
1440, fresh context, `GET /categories` during the outage: the **document** came back as `503 application/json`. The browser displayed `{"message":"Service is temporarily unavailable"}` on a blank page (`V20-BEFORE-1440-categories-document-json.png`, opened). Instance log: `[og-middleware] bounded dependency failure for /categories canceling statement due to lock timeout`.

The client's error card and Retry branch (`categories-error-card`, `CatalogError`) could never appear on a cold load, because the app never booted. This is exactly the gap the item describes. In earlier passes the branch was only ever "reached" through warm-cache/offline states.

**Root cause:** `server/og-middleware.ts` caught a bounded dependency failure during route-meta resolution and answered every request with `res.status(503).json(…)`. Browser navigations got the same answer.

**Fix (targeted, own region of og-middleware):** requests that do not accept `text/html` still get the generic JSON 503. That includes the cheap cache-admission rejection that the `task302-resilience` gate probes deliberately without an Accept header, so the gate's contract is unchanged. Browser navigations (`Accept: text/html`) now fall through with `defaultMeta(urlPath)` and a `dependencyUnavailable` flag. The buffered `res.end` stamps **HTTP 503 + `Retry-After: 1`** on the SPA shell, the same way the soft-404 stamps 404. The status code still tells crawlers the outage is transient, and the visitor gets the app's own error UI.

## Gate compatibility
The `catalog-database-resilience.ts` SSR cache-admission probe sends no Accept header and still expects `503` + JSON `message` + `Retry-After: 1`. That path is unchanged, and the gate is re-run in the final gate pass (see STATUS.md).

## Residue
None created. The scenario is read-only, and the lock was released by COMMIT. Instance D was killed by its own process group, and `pg_locks` shows 0 AccessExclusive locks on `resources`.
