# V12 — /admin/users role change, user deletion, and two-user isolation

**Status: PASS (after a fix). Proven on DEV (real app :5000, real Chromium, backend-minted Clerk users) at 1440 and 402, 2026-10-10.**
One defect was found and fixed: after a confirmed delete, keyboard focus fell to `<body>` instead of the user search box.

## How it was run

```bash
node docs/audit-578/verify/task592-harness/v12-admin-users.mjs desktop --isolation
node docs/audit-578/verify/task592-harness/v12-admin-users.mjs 402
```
Raw output: `task592-harness/out/V12-desktop.json`, `V12-402.json`.
In each run the script mints these Clerk users:
- an admin (`…v12adm…`; local role set to admin by SQL after JIT provisioning)
- a role target (`…v12role…`)
- a delete target (`…v12del…`)
- with `--isolation`: users A and B

The delete target owns one bookmark, one favorite, one API key, one submitted resource (`POST /api/resources` → 201, pending) and one pending edit. The edit was inserted by SQL because a real edit submission triggers paid background AI.

| Clerk | `GET /users/<id>` → 404 |

### Defect and fix
`AlertDialogAction` closes the dialog on click. Radix therefore returned focus to the row's Delete trigger before the mutation resolved, so `onCloseAutoFocus` ran while `deletedUserRef` was still false. When the refetch removed the row, the trigger unmounted and focus dropped to `<body>`.
The fix is in `client/src/components/admin/UsersTab.tsx`:
- `onSuccess` now also focuses the search input directly.
- The Delete trigger resets `deletedUserRef` when it opens, so a leftover flag cannot redirect a later Cancel.

The first run (before the fix) recorded `"focus":"BODY"`; both runs after the fix recorded `input-user-search`.

## Two-user isolation (A owns everything, B attacks; desktop run)

A owns a collection, a bookmark with a private note, an API key, a pending submission, journey progress (start 200) and an in-app notification.

| B's request against A's ids | Status | Leaks A? |
|---|---|---|
| PATCH / POST publish / DELETE A's collection | 404 / 404 / 404 | no |
| GET a single collection | 405 (no such route) | no |
| DELETE A's API key | 404 | no |
| DELETE (withdraw) A's submission | 404 | no |
| PATCH A's notification read | 404 | no |
| GET own bookmarks / collections / submissions / api-keys / notifications | 200 each | no (none contains A's id, note, names or titles) |
| GET journey progress (B never started) | 404 | no |
| non-admin GET /api/admin/users, PUT role, DELETE user | **403 / 403 / 403** | no |

A's state after B's attempts: collection name unchanged, unpublished, 1 key, submission still pending, notification unread, role `user`.
Positive control, the owner A on the same ids: revoke key 200, withdraw submission 200, mark notification read 200, delete collection 200.
