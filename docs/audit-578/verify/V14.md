## Run 1: paid run started through the UI on A, before the fix (job 44)

1. At 1440px: `/admin/enrichment` → opened "Job controls & monitoring" → Filter **Unenriched Only** → Batch size **1** → **Start Enrichment**.

3. A concurrent `POST /api/enrichment/start` returned `409 "Enrichment job #44 is already processing. Wait for it to finish or cancel it before starting a new one."`
4. Polled `GET /api/enrichment/jobs/44` and `/events?afterSeq=N`:
   - The job went `processing 0/1` → `completed 1/1` (successful 1, failed 0).
   - 13 events with strictly increasing `seq` (`polledInOrder: true`). Event types: lifecycle, message, tool_call, tool_result, result. The first event was "Run started (model cc/claude-haiku-4-5-20251001, maxTurns 16, budget $0.08)".
   - `afterSeq=<last>` returned `[]`.
   - Cost $0.0189.
5. No secrets appeared in the job or event JSON. The scan checked every configured secret value and `authTokenEncrypted`, and the job carries no `authTokenEncrypted` field.
6. R2 metadata stayed byte-identical.
7. R1 received a `resource_audit_log` row: `ai_enriched`, "AI enrichment completed with confidence 0.95".
8. **Defect observed.** R1 got `aiEnriched: true` and `suggestedTags`, but `metadata.tags` stayed absent. In run 2 the queue then held **2** items, R1 and R3, because R1 was picked up again as "unenriched".

## Root cause and fix

- The "Unenriched Only" filter (`queueBatchEnrichment`) and `GET /api/admin/enrichment/coverage` both count resources with no `metadata.tags`.
- `applyEnrichment` stored the model's tags only as `metadata.suggestedTags`. Nothing in the server ever promotes `suggestedTags` (checked with grep).
- Live impact before the fix: DEV had **5** approved resources that were AI-enriched but still untagged, left by earlier runs. Production has 2775 untagged approved resources, so any production enrichment run would never close the gap and would pay again for the same rows on every run.
- **Fix**: when the resource has no tags, `applyEnrichment` now also writes the AI tags to `metadata.tags`. The tags are entity-decoded, whitespace-collapsed, trimmed to 50 characters, deduplicated case-insensitively, and capped at 5. Existing tags are never overwritten, which is why R2 stays unchanged.

## Follow-up resolution (task 621, 2026-10-10)

The residual gaps above are now fixed in code and re-proven on DEV:

- **Cancelled jobs close out their queue.** Cancelling an enrichment job flips the job and its unprocessed queue rows in one transaction. The rows become `cancelled` with the reason "Not processed: the job was cancelled". Failed, budget-stopped and orphaned jobs get the same close-out with their own reasons. Job counters are not bumped, because those resources were never processed.
- **No 409 window after a restart.** Each enrichment and research job row now records its worker process (`worker_id`) and a `heartbeat_at` refreshed every 10 s (migration `0054_ai_job_worker_liveness`). An active row counts as orphaned when its owner is provably dead (same container, pid gone) or its heartbeat is older than 45 s. Rows from before this change keep the 5-minute age rule. Enrichment admission reclaims an orphan inside its locked transaction instead of returning 409. The boot sweep reclaims same-container orphans immediately, and the periodic sweep now runs every 60 s. A row owned by a live sibling instance (fresh heartbeat) still blocks with 409 and is never swept.
- **Budget stops have their own status.** A run ended by its USD cap is saved as `budget_stopped`, whether the SDK returns or throws the budget result. The admin UI shows it as "Stopped at budget" in warn tone. Reaching the discovery target still counts as `completed`.

Evidence (DEV):
- DB probe with scratch enrichment rows, all deleted afterwards:
  - cancel → 3/3 queue rows `cancelled`
  - live sibling → `ENRICHMENT_JOB_ACTIVE`, and the sweep left it alone
  - dead-pid owner with a heartbeat from just now → admission reclaimed it (failed, "Orphaned by server restart", queue closed out) and admitted the new job with no 409
  - stale heartbeat from another container → swept
  - locally owned row → never swept
- The research restart proof in V15 exercises the same boot sweep.

Review hardening (same task):
- **Returned budget result stops enrichment.** If a batch's SDK result comes back (not thrown) as `error_max_budget_usd` with items still unsubmitted, the batch now stops the job. Before this, the loop re-ran those items and paid again, and the job ended `completed`. Usage is kept, the job becomes `budget_stopped`, and leftover queue rows are closed out. Unit coverage for both result shapes is in `tests/unit/ai-job-liveness.test.ts`.
- **Orphan flips are race-safe.** Each orphan flip (watchdog for both job types, and enrichment admission) now also requires the `worker_id` and `heartbeat_at` it read. A heartbeat written between the liveness read and the flip makes the flip match nothing. Admission then still returns 409 for that live job.
- DB race probe (scratch rows, deleted): stale read → heartbeat → guarded flip = 0 rows, still `processing`. An unchanged stale row → guard matches and the sweep flips it. A dead-pid orphan and an old legacy row → admission reclaimed both, no 409.
