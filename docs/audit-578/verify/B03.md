# B03 — Progress accepted partially invalid step arrays

**Status: FIXED and proven** on DEV, 2026-10-09 (real signed-in Clerk user via curl/fetch).

## Before (audit evidence)
After journey 7's groups were completed, `PUT /api/journeys/7/progress {"stepIds":[181,"bad"],"completed":false}` → **200**, and 181 was removed from stored completion. The handler filtered out non-integers instead of rejecting the payload.

## Fix
`PUT /api/journeys/:id/progress` now validates the whole payload before any write:
- Exactly one of `stepId` or `stepIds`.
- `stepIds` must be 1–100 unique positive int4 integers, and `completed` must be a boolean.
- Anything else → `400 "Provide either stepId or 1–100 unique positive integer stepIds"` with no mutation.
- Foreign step ids keep their 422.

## Proof (`api-proof.json` → `B03`)
Throwaway user started journey 7. Valid group `[181,182,183]` completed → 200 with `logicalStepCompleted:true` the first time, `false` on repeat (transition flag fires once). `completedSteps` = `[181,182,183]`.

| Body | Status | Progress unchanged |
|---|---|---|
| `{"stepIds":[181,"bad"],"completed":false}` | 400 | yes |
| `[181,null]` | 400 | yes |
| `[181,1.5]` | 400 | yes |
| `[181,2147483648]` (int overflow) | 400 | yes |
| `[181,-4]` | 400 | yes |
| `[]` | 400 | yes |
| `[181,181]` (duplicates) | 400 | yes |
| `"181"` (not an array) | 400 | yes |
| 101 ids | 400 | yes |
| `stepId` + `stepIds` | 400 | yes |
| `completed:"no"` | 400 `completed must be a boolean` | yes |
| foreign step 199 | 422 `Step ID(s) do not belong to this journey: 199` | yes |

"Progress unchanged" means the user's `GET /api/journeys/7/progress` was compared before and after each request.

Clerk user deleted, then the local row. Residue is 0 (see B01.md).
